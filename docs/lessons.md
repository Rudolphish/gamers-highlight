# 進め方の記録

**`CLAUDE.md` との違い**: あちらは「このコードを触るときに知っておくべきこと」。
こちらは「**作業の進め方でやらかしたこと**」——確認の仕方、道具の使い方、判断の順序。
コードを読んでも絶対に分からないので、書き残さないとセッションが変わるたびに同じ穴に落ちる。

`CLAUDE.md` と同じ方針で、**一般論は書かない。** ここに載っているのは全て一度やらかしたこと。
「〜すべき」で終わる項目は書かない。**何が起きて、どう間違えたか**を残す。

## 確認

### テストは「落ちること」を見るまで書けたことにならない

キャッシュ無効化のテスト（F68）が通ったので直ったと判断したが、**通った理由が
別のテスト（F67）がその前にタグを流していたから**だった。順序を入れ替えたら落ちた。
実装から無効化を消しても通るテストは、何も確認していない。

以来、修正のテストを足したら**修正を外したビルドで実際に落ちることを確認**している。
#41 の後追いで足した F57b はこの手順で確認し、修正前は `www.googleapis.com` を
引いてしまうことを目視した。手間は「ビルド1回＋実行1回」。この確認を省いた回は
必ず後で「実は効いていなかった」が出ている。

### 「そうなるはず」の初期状態で試すと、直っていなくても通る

アルバムの並び順の修正で、「投稿したアルバムが先頭に来る」テストを**新しく作ったアルバム**で書いた。
作ったばかりのアルバムは何もしなくても先頭に来るので、**修正を外したビルドでも通った**。
見ていたのは「投稿で上がったのか、新しいから上にいるのか」を区別できない位置だった。

先に別のアルバムを上げて**自分のアルバムを下に沈めてから**投稿する形に書き直したら、
修正を外したビルドで落ちるようになった。**期待する結果と同じ初期状態から始めない。**

### 単体で通るテストが、通しで流すと落ちる（逆も同じ）

アルバムの並び替えのテストを、表示順の**位置**（1番目・2番目…）で書いた。単体では通ったが
`run-all.mjs` で流すと落ちた。**flows が同じグループにアルバムを1件作る**（Discordタグ経由の
"eldenring"）ため、通しのときだけ件数が増えて位置がずれる。

スイートは同じDBを順番に使うので、**後ろのスイートは前のスイートが足したデータを見る**。
自分で仕込んだデータの**相対順序**だけを見るように書き直した（無関係な行は名前で除外する）。

同じ理由で、枚数のように他のスイートが動かしうる値は**絶対値で断定しない**。
「降順であること」「触られない0枚のアルバムが後ろに来ること」のように、
増減があっても成り立つ形にする。

### 文字列一致でソースを判定すると、コメントに当たる

写真リアクションのAPIは意図的にキャッシュを無効化しない。その理由をコメントに書いたら、
**そのコメントに含まれる `cacheTags` という単語**に2つの仕組みが反応した——テスト（F82）が
`routeSource.includes("cacheTags")` で落ち、`audit-invalidation.mjs` は「書き込みなのに
無効化を呼んでいない」でCIを落とすところだった。どちらも**実際のimport文と呼び出し**を見る形に直した。

あわせて `audit-invalidation.mjs` に「意図的に無効化しない」と宣言する印を足した。
黙って対象外にすると、本当の呼び忘れと区別がつかず、この道具を作った理由が消えるため。

### 画面に重なりがあるテストは、見る範囲を絞る

Lightbox（全画面の重ね表示）の❤️を数えたつもりが、**背後のグリッドに残っているボタンも
一緒に数えていた**。判定はLightbox内だけに絞る必要があった。

重ねて表示するものは前のDOMが消えない。`document` 全体を数える判定は、
たいてい期待と違うものを見ている。

### 1回しか実行しないと、2回目に壊れるものが見つからない

`unstable_cache` は値をJSONで保存するため、Prismaの `Date` が2回目からISO文字列で返る。
`capturedAt?.toISOString()` は**キャッシュヒットの回だけ**落ちる。1回目は素の `Date` が返るので
通ってしまい、権限マトリクスの確認で初めて出た（F62b・F64b は必ず2回開くようにしてある）。

**テスト自身が状態を残す側になることもある。** ブラウザスイート（B）を同じDBに2回流したら3件落ちた。
❤️を押したまま・説明を書いたまま終わっていたため、2回目は「押す」が「取り消す」になっていた。
**CIは毎回まっさらなDBなので、CIでは絶対に出ない**——手元で流し直したときだけ落ち、つまり
「自分の変更が壊した」と誤読する形で出る。書き換えるテストは始める前に状態をならし、終わったら戻す
（`browser.mjs` の `clearAllHearts` / `clearDescription`）。CIに載せる前に**2回連続で流す**。

### 確認の道具が壊れていても、結果は「0件」で普通に返ってくる

3回やった。**どれも「アプリが壊れている」ようにしか見えず、疑う先を間違えた。**

- **後片付けをDB直で書いた（F96・F97）。** `db.photo.deleteMany` はAPIを通らないので
  `invalidateAlbumPhotos` が呼ばれず、アルバムのキャッシュに消えた写真が残る。次に走る
  ブラウザスイートがそれをクリックして❤️も説明も落ちた（B34・B36・B39・B41）。症状は
  「❤️が効かない」で、しかもサーバー起動直後の初回だけ（CIでは毎回、手元では2回目以降は通る）。
  **決め手は `context.on("response")` で4xxを拾ったこと**——`404 POST /api/photos/<消えたID>/reactions`
  が出て推測が要らなくなった。最初の仮説は合っていたのに、HTMLを1回curlしただけで外していた。
  → **作ったデータは、作ったときと同じ経路（API）で消す。**
- **cronのルートは `fetch-stub` を通らない**（手動送信は通る。本番ビルドのルートごとのバンドルの違い）。
  「cronは `posted: 1` を返すのにスタブの記録は0件」で止まり、`/tmp/stub-calls.log` の件数を
  送信の前後で数えて確定させた。まずいのは、気づく前に**「壊して確認」を回してしまった**こと。
  落ちたのは観測手段が壊れていたからで、確認になっていなかった。しかも `next-server` が2つ動いており
  （片方はスタブ無し）、**下に書いてある「ポートが空いたことを確認してから起動する」を自分で守っていなかった。**
  → cron側の判定は**DBに残る記録**（`AppSetting`）で見る。文面はスタブを通る手動送信の側で確認する。
- **Reactは隣り合うテキストを区切る。** JSXで `{emoji} {count}` と並べるとHTMLは
  `📷<!-- --> <!-- -->3` になり、`/📷 (\d+)/` が当たらない。活動カレンダーのテストが5件同時に落ちた。
  先にあった週次まとめのテスト（F100）が同じ書き方で通っていたのは、画面の数字ではなく `<pre>` に
  出しているDiscordの文面（1つの文字列）に当たっていたから。
  → **確認したい値は1つの文字列として描く**（`` {`${emoji} ${count}`} ``）。

**環境の健全性を先に確かめる。** そこが壊れていると、壊して確認する手順ごと無意味になる。

### 根拠にならないものを根拠にしない

- **測っていない説明は憶測。** 自動レビューが飛んでいた件で「コンテナの再起動でセッションが
  切れたせいだ」と書いてPRに載せたが、間違いだった。`getPendingCommits` が起点を辿れないときに
  黙って引き直しており、10ブランチ分を数えたら9本の初回コミットが該当していた。再起動は関係なかった。
- **コメントは動作の証拠ではない。** `refresh/route.ts` には「埋まっている項目は引き直さないので
  クォータを食わない」と書いてあったが、実装はそうなっていなかった（`need` を渡していなかった）。
  書いた時点の意図が残っていただけで、レビューで指摘されるまで半月気づかなかった。

## 自動で走る仕組み

### 「走らなかった」が見えない仕組みは、壊れていても気づけない

自動レビューは新しいブランチの最初のコミットを毎回飛ばしていたが、**飛ばしたことを
`console.error` に出すだけで台帳にもログにも残していなかった。** 外からは
「PASSした」のか「そもそも走らなかった」のかが区別できず、6本のブランチが
丸ごと未レビューのままマージされていた。

**沈黙を成功と解釈できる状態を作らない。** 見送るなら見送ったと記録する。
記録の無い分岐を1つでも残すと、そこだけが永久に死角になる。

### 可視化のために足した記録が、判定にも使われると逆効果になる

上の対策で「見送り」を台帳に `SKIP` 行として残すようにしたが、台帳は
「レビュー済みのコミット一覧」を作るのにも使われている。**`SKIP` をそこに数えると、
見送った瞬間にそのコミットが恒久的にレビュー対象から外れる**——見落としを可視化する
ために足した行が、見落としを固定化する。

記録を足すときは、**その記録を読んでいる既存の処理を全部洗う。**

### 実行中のプロセスが書くファイルを、バックアップから復元してはいけない

フックの動作確認のため台帳をバックアップして復元していたが、その裏で後追いレビューが
同じ台帳に追記していた。復元した瞬間に **#40 のレビュー記録が消えた**（レビュー自体は
`docs/review-log/` に残っていたので、行を戻して復旧できた）。

バックアップ＆復元は「他に誰も書いていない」が前提。並行して動かすなら、
**復元ではなく差分で戻す**か、そもそも別ファイルに向ける。

### 手順を決める前に、禁止されている操作を見る

squashマージ後に同じブランチ名で続きを出そうとして `git push --force-with-lease` を3回試し、
3回とも弾かれた。原因は `.claude/settings.json` の deny にある `Bash(*git push*--force*)`。
**その場の判断ではなくリポジトリのポリシー**なので何度試しても通らないが、拒否は理由を伝えて
くれないため「ユーザーが渋っている」と読み違えて確認の往復を2回挟んだ。

**止まる層は2つあり、事前に見られるのは片方だけ。**

| 層 | 例 | 事前に一覧で見られるか |
|---|---|---|
| 設定（`.claude/settings.json` の `deny`） | force push・`prisma db push`・`rm -rf`・本番デプロイ | **見られる。手順を決める前に読む** |
| 認証（プロキシ） | `git push origin --delete` が **HTTP 403**（GitHub MCP にも削除ツールは無い） | 見られない。一度試して駄目なら手順を渡す |

`git push` は ref の削除に失敗しても「Everything up-to-date」と出す。`-v` を付けるまで403が見えなかった。
リモートブランチの削除は、GitHubのbranches画面かユーザーの手元でしかできない。

## ローカル環境

### `pkill` は親だけ殺して子が生き残る

修正前のビルドでテストが落ちることを確認しようとして `pkill -f "next start"` したが、
死んだのは pnpm のラッパーだけで `next-server` の子プロセスが3000番を掴んだまま残った。
新しいサーバーは `EADDRINUSE` で起動に失敗し、**テストは古い（修正済みの）サーバーに
当たって 0 NG を返した。** 危うく「テストが効いている」と誤認するところだった。

サーバーを入れ替えるときは、**ポートが空いたことを確認してから**起動する。

```bash
ps aux | grep next-server | grep -v grep | awk '{print $2}' | xargs -r kill -9
lsof -ti :3000    # 何も出なければ空き
```

（以前ここには `ss -ltn` と書いてあったが、**`ss` も `netstat` もこのコンテナには無い**。
実際に踏んで `command not found` になった。）

### 本番ビルドはコードを変えても勝手に入れ替わらない

`tools/local-test` は `next build && next start` で確認する（`dev` だとNext.js自身の
エラーオーバーレイが出てアプリ側のエラーバウンダリが見えないため）。つまり
**ソースを直しただけではテストに反映されない。** ビルドし直してサーバーを再起動するまで、
見ているのは前のコードの挙動。

**組み直す対象はWebだけではない。** Botの遡り取り込みのテストは `apps/bot/dist` を読むので、
壊して確認した後に `apps/bot` を組み直し忘れ、**関係ない回で落ち続けた**
（Webだけ組み直す手元のスクリプトを使っていたため）。dist を読むテストを足したら、
その dist を作る手順も同じところに足すこと。

### リポジトリルートで `npm install` を実行しない

pnpmワークスペースなので、`node_modules` が 182 → 18 に刈り込まれて動かなくなる。
戻すには `pnpm install` と `npx prisma generate`。

## レビュー

### 自分で書いた直後のコードは、自分では見えない

飛ばされていた7件を後から掛け直したら **6件PASS・1件FAIL** で、FAILは
「コメントと実装が食い違い、クォータ枯渇を悪化させる」という実害のあるものだった。
どれも自分でテストを通してマージしたコードで、その時点では問題無いと判断していた。

別プロセスのレビュー（`.claude/hooks/auto-review.mjs`）を挟む価値はここにある。
**マージ前に `node .claude/hooks/review-status.mjs --range` で確認すること。**

### 台帳の列は複数値を持ちうる

`review-status.mjs` を作ったとき、台帳の `commits` 列を単一SHAとして扱った。
実際はまとめてレビューした場合に `;` 区切りで複数入る。**レビュー済みのコミットが
軒並み「未レビュー」に見える**という、このツールの信頼を落とす一番まずい壊れ方をした
（レビューで指摘されて気づいた）。

書く側の形式は、読む側を書く前に**実物を見る**。

## CI

### サードパーティのactionは落ちる。標準で足りるなら使わない

CIの最初の実行が、テストを1つも動かさないまま両ジョブとも落ちた。原因は
`pnpm/action-setup` のダウンロードが **429 Too Many Requests**（3回リトライして力尽きる）。
自分のコードは1行も関係していない。

再実行すれば通っただろうが、**同じ落とし穴がそのまま残る**ので `corepack` に替えた
（Nodeに同梱なのでダウンロードが無い。しかもバージョンは `package.json` の
`packageManager` から取るので、workflow側との二重管理も消えた）。

CIの前段（action取得・依存インストール）は自分の管理外で落ちる。
**外せる外部依存は外す**——リトライで済ませると、次に同じ場所で止まる。

## 書き足すルール

- **足すのは「一度やらかしたこと」だけ。** 予防的な心得は書かない。増えるほど読まれなくなる
- 自動レビューが **FAIL** を出したら、直したあとにここへ1項目足す。
  コードの落とし穴（この関数はこう呼ぶ、この順序で書く）なら `CLAUDE.md` の方へ
- **何が起きたか**を具体的に書く。「〜に注意」だけの項目は、次に読んだとき判断に使えない
- 同じ話が2箇所に増えたら統合する。このファイルは長さではなく**読まれることが価値**
- **8192文字**（バイト数ではない）を超えるとセッション開始時に警告が出る。出たら古い項目を畳む
