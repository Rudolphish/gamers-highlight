# 進め方の記録

**`CLAUDE.md` との違い**: あちらは「このコードを触るときに知っておくべきこと」。
こちらは「**作業の進め方でやらかしたこと**」——確認の仕方、道具の使い方、判断の順序。
コードを読んでも絶対に分からないので、書き残さないとセッションが変わるたびに同じ穴に落ちる。

`CLAUDE.md` と同じ方針で、**一般論は書かない。** ここに載っているのは全て一度やらかしたこと。
「〜すべき」で終わる項目は書かない。**何が起きて、どう間違えたか**を残す。

## 確認

### テストは「落ちること」を見るまで書けたことにならない

キャッシュ無効化のテスト（F68）が通ったので直ったと判断したが、**通った理由が
別のテスト（F67）がその前にタグを流していたから**だった。順序を入れ替えたら落ちた。
実装から無効化を消しても通るテストは、何も確認していない。

以来、修正のテストを足したら**修正を外したビルドで実際に落ちることを確認**している。
#41 の後追いで足した F57b はこの手順で確認し、修正前は `www.googleapis.com` を
引いてしまうことを目視した。手間は「ビルド1回＋実行1回」。この確認を省いた回は
必ず後で「実は効いていなかった」が出ている。

### 単体で通るテストが、通しで流すと落ちる（逆も同じ）

アルバムの並び替えのテストを、表示順の**位置**（1番目・2番目…）で書いた。単体では通ったが
`run-all.mjs` で流すと落ちた。**flows が同じグループにアルバムを1件作る**（Discordタグ経由の
"eldenring"）ため、通しのときだけ件数が増えて位置がずれる。

スイートは同じDBを順番に使うので、**後ろのスイートは前のスイートが足したデータを見る**。
自分で仕込んだデータの**相対順序**だけを見るように書き直した（無関係な行は名前で除外する）。

同じ理由で、枚数のように他のスイートが動かしうる値は**絶対値で断定しない**。
「降順であること」「触られない0枚のアルバムが後ろに来ること」のように、
増減があっても成り立つ形にする。

### 文字列一致でソースを判定すると、コメントに当たる

写真リアクションのAPIは意図的にキャッシュを無効化しない。その理由をコメントに書いたら、
**そのコメントに含まれる `cacheTags` という単語**に2つの仕組みが反応した。

- 自分で書いたテスト（F82）が `routeSource.includes("cacheTags")` で落ちた
- `audit-invalidation.mjs` が `source.includes("cacheTags")` で対象と判断し、
  「書き込みなのに無効化を呼んでいない」でCIを落とすところだった

どちらも**実際のimport文と呼び出し**を見る形に直した。
「そのファイルが何をしているか」を知りたいときに、素の文字列一致で済ませない。

あわせて `audit-invalidation.mjs` に「意図的に無効化しない」と宣言する印を足した。
黙って対象外にすると、本当の呼び忘れと区別がつかず、この道具を作った理由が消えるため。

### 画面に重なりがあるテストは、見る範囲を絞る

Lightbox（全画面の重ね表示）の❤️を数えたつもりが、**背後のグリッドに残っているボタンも
一緒に数えていた**。判定はLightbox内だけに絞る必要があった。

重ねて表示するものは前のDOMが消えない。`document` 全体を数える判定は、
たいてい期待と違うものを見ている。

### 1回しか実行しないと、2回目に壊れるものが見つからない

`unstable_cache` は値をJSONで保存するため、Prismaの `Date` が2回目からISO文字列で返る。
`capturedAt?.toISOString()` はキャッシュヒットの回だけ落ちる。**1回目は素の `Date` が
返るので通ってしまう。** テストで1回開いただけだったので見逃し、権限マトリクスの確認で
初めて出た（`tools/local-test/flows.mjs` の F62b・F64b は必ず2回開くようにしてある）。

同じ形の落とし穴は「初回だけ」「2回目だけ」「日付が変わったら」全部にある。
**状態を持つものは、状態が変わった後をもう一度通す。**

**テスト自身が状態を残す側になることもある。** ブラウザスイート（B）をCIに載せるとき、
同じDBに2回流したら3件落ちた。❤️を押したまま・説明を書いたまま終わっていたため、
2回目は「押す」が「取り消す」に、「説明を書く」が「編集」になっていた。
**CIは毎回まっさらなDBなので、CIでは絶対に出ない。** 手元で流し直したときだけ落ちる
——つまり「自分の変更が壊した」と誤読する形で出る。書き換えるテストは、
**始める前に状態をならし、終わったら戻す**（`browser.mjs` の `clearAllHearts` /
`clearDescription`）。CIに載せる前に**2回連続で流して**同じ結果になることを見ておく。

### テストの後片付けをDB直で書くと、キャッシュに残って次のスイートを壊す

活動ログのテスト（F96・F97）で作った写真を、後片付けに `db.photo.deleteMany` で
直接消していた。**API経由ではないので `invalidateAlbumPhotos` を通らない。**
アルバムのキャッシュには消えた写真が残り続け、次に走るブラウザスイート（B）が
その写真をクリックして、❤️も説明も **404 で落ちた**（B34・B36・B39・B41）。

厄介だったのは出方で、**アプリのバグにしか見えない**。
「❤️が効かない」「説明が保存できない」という画面の症状で、しかも
**サーバー起動直後の初回だけ**（＝CIでは毎回、手元では2回目以降は通る）。
自分の変更が壊したと思い込んで、アプリ側を疑い続けるところだった。

- 最初の仮説（キャッシュに消えた写真が残っている）は**合っていたが、確かめ方が雑で外した**
  ——アルバムページのHTMLを1回curlで取って「ゴーストは無い」と誤判定した
- 決め手は**ブラウザの通信を記録すること**だった。
  `context.on("response")` で4xxを拾ったら `404 POST /api/photos/<消えたID>/reactions` が出て、
  それ以上の推測が要らなくなった

**作ったデータの後片付けは、作ったときと同じ経路（API）で消す。**
DBを直に触ってよいのは、キャッシュに載らないものだけ。

### スタブに記録が無い＝送っていない、ではない

週次通知のテストで「cronは `posted: 1` を返すのに、fetchスタブの記録が0件」という状態に
はまった。**ルートによってスタブを通るかどうかが違った。**

| 経路 | fetch-stub |
|---|---|
| 手動送信（`/api/admin/weekly-notify`） | 通る |
| cron（`/api/cron/check-bot-health`） | **通らない**（実ネットワークへ出る） |

同じプロセス・同じ `postDiscordMessage` なのにこうなる（本番ビルドのルートごとの
バンドルの違い）。`/tmp/stub-calls.log` の件数を送信の前後で数えて確定させた。

まずかったのは、この事実に気づく前に**「壊して確認」を回してしまった**こと。
落ちたテストを見て「壊した箇所が検知された」と読んだが、実際は観測手段が壊れていただけで、
確認になっていなかった。**環境の健全性を先に確かめないと、壊して確認する手順ごと無意味になる。**

しかも同時に `next-server` が2つ動いており（片方はスタブ無し）、
`lessons.md` に書いてある「ポートが空いたことを確認してから起動する」を自分で守っていなかった。
**書いてある手順を飛ばした回に、書いてあるとおりの事故が起きた。**

対策として、cron側の判定は**DBに残る記録**（`AppSetting`）で見るようにした。
ネットワークにもスタブにも依存しないので、CIでも同じ結果になる。
文面の中身は、スタブを通る手動送信の側で確認している。

### 画面の文字列で確認するとき、Reactは数字を切り離して出す

活動カレンダーのテスト5件が同時に落ち、**どれも「件数が0」という出方**をした。
実装ではなく確認の側が壊れていた。JSXで `{emoji} {count}` と並べると、
HTMLは `📷<!-- --> <!-- -->3` になる（Reactが隣り合うテキストを区切るため）。
`/📷 (\d+)/` は当たらず、**0件として読める——機能が動いていないのと区別がつかない。**

紛らわしいのは、先にあった週次まとめのテスト（F100）が同じ書き方で通っていたこと。
あれが当たっていたのは画面の数字ではなく、`<pre>` に出している**Discordの文面**
（`formatWeeklySummaryText` が組み立てた1つの文字列）の方だった。

**確認したい値は1つの文字列としてレンダリングする**ようにした（`{\`${emoji} ${count}\`}`）。
表示は同じで、外から読める形になる。

### 原因を断定する前に測る

自動レビューが飛んでいた件で、最初「コンテナの再起動でセッションが切れたせいだ」と
書いてPRに載せた。**間違いだった。** コードを読み直すと `getPendingCommits` が
起点を辿れないときに黙って引き直しており、10ブランチ分を数えたら9本の初回コミットが
該当していた。再起動は関係なかった。

もっともらしい説明は、測っていないなら**ただの憶測**。数えられるものは数えてから書く。

### コメントを根拠に正しさを判断しない

`refresh/route.ts` には「埋まっている項目は引き直さないので、短い間隔でもクォータは
食わない」と書いてあった。**実装はそうなっていなかった**（`need` を渡していなかった）。
コメントは書いた時点の意図であって、動作の証拠ではない。レビューで指摘されるまで
半月気づかなかった。

## 自動で走る仕組み

### 「走らなかった」が見えない仕組みは、壊れていても気づけない

自動レビューは新しいブランチの最初のコミットを毎回飛ばしていたが、**飛ばしたことを
`console.error` に出すだけで台帳にもログにも残していなかった。** 外からは
「PASSした」のか「そもそも走らなかった」のかが区別できず、6本のブランチが
丸ごと未レビューのままマージされていた。

**沈黙を成功と解釈できる状態を作らない。** 見送るなら見送ったと記録する。
記録の無い分岐を1つでも残すと、そこだけが永久に死角になる。

### 可視化のために足した記録が、判定にも使われると逆効果になる

上の対策で「見送り」を台帳に `SKIP` 行として残すようにしたが、台帳は
「レビュー済みのコミット一覧」を作るのにも使われている。**`SKIP` をそこに数えると、
見送った瞬間にそのコミットが恒久的にレビュー対象から外れる**——見落としを可視化する
ために足した行が、見落としを固定化する。

記録を足すときは、**その記録を読んでいる既存の処理を全部洗う。**

### 実行中のプロセスが書くファイルを、バックアップから復元してはいけない

フックの動作確認のため台帳をバックアップして復元していたが、その裏で後追いレビューが
同じ台帳に追記していた。復元した瞬間に **#40 のレビュー記録が消えた**（レビュー自体は
`docs/review-log/` に残っていたので、行を戻して復旧できた）。

バックアップ＆復元は「他に誰も書いていない」が前提。並行して動かすなら、
**復元ではなく差分で戻す**か、そもそも別ファイルに向ける。

### 手順を決める前に、禁止されている操作を見る

squashマージ後に同じブランチ名で続きを出そうとして `git push --force-with-lease` を
3回試し、3回とも弾かれた。原因は `.claude/settings.json` の deny に
`Bash(*git push*--force*)` があること。**その場の判断ではなくリポジトリのポリシー**なので、
何度試しても通らない。しかも拒否は理由を伝えてくれないため、
「ユーザーが渋っている」と読み違えて確認の往復を2回挟んだ。

`.claude/settings.json` の `deny` は**この環境で構造的にできないこと**の一覧
（force push・`prisma db push`・`rm -rf`・本番デプロイなど）。
やり方を提案する前にここを見る。拒否が続いたら、まず自分の選んだ手が
禁止側に入っていないかを疑う。

**ただし禁止は1箇所には書かれていない。** 続けてマージ済みブランチを片付けようとしたら、
今度は `git push origin --delete` が **HTTP 403** で落ちた。こちらは `deny` に無い——
通常の push は通るのに、**プロキシ経由の認証が ref の削除だけ許していない**（`--delete` と
`:branch` の両方の書き方、リトライでも同じ）。GitHub MCP 側にもブランチ削除のツールは無い。
`git push` は「Everything up-to-date」と出すので、`-v` を付けるまで403が見えなかった。

つまり**設定で止まるもの（settings.json）と、認証で止まるもの（403）は別の層**にある。
後者は事前に一覧で確認する方法が無いので、**一度試して駄目なら諦めて手順を渡す**ほうが速い。
リモートブランチの削除は、GitHubのbranches画面かユーザーの手元でしかできない。

## ローカル環境

### `pkill` は親だけ殺して子が生き残る

修正前のビルドでテストが落ちることを確認しようとして `pkill -f "next start"` したが、
死んだのは pnpm のラッパーだけで `next-server` の子プロセスが3000番を掴んだまま残った。
新しいサーバーは `EADDRINUSE` で起動に失敗し、**テストは古い（修正済みの）サーバーに
当たって 0 NG を返した。** 危うく「テストが効いている」と誤認するところだった。

サーバーを入れ替えるときは、**ポートが空いたことを確認してから**起動する。

```bash
ps aux | grep next-server | grep -v grep | awk '{print $2}' | xargs -r kill -9
ss -ltn | grep -q :3000 && echo "まだ使用中" || echo "空き"
```

### 本番ビルドはコードを変えても勝手に入れ替わらない

`tools/local-test` は `next build && next start` で確認する（`dev` だとNext.js自身の
エラーオーバーレイが出てアプリ側のエラーバウンダリが見えないため）。つまり
**ソースを直しただけではテストに反映されない。** ビルドし直してサーバーを再起動するまで、
見ているのは前のコードの挙動。

### リポジトリルートで `npm install` を実行しない

pnpmワークスペースなので、`node_modules` が 182 → 18 に刈り込まれて動かなくなる。
戻すには `pnpm install` と `npx prisma generate`。

## レビュー

### 自分で書いた直後のコードは、自分では見えない

飛ばされていた7件を後から掛け直したら **6件PASS・1件FAIL** で、FAILは
「コメントと実装が食い違い、クォータ枯渇を悪化させる」という実害のあるものだった。
どれも自分でテストを通してマージしたコードで、その時点では問題無いと判断していた。

別プロセスのレビュー（`.claude/hooks/auto-review.mjs`）を挟む価値はここにある。
**マージ前に `node .claude/hooks/review-status.mjs --range` で確認すること。**

### 台帳の列は複数値を持ちうる

`review-status.mjs` を作ったとき、台帳の `commits` 列を単一SHAとして扱った。
実際はまとめてレビューした場合に `;` 区切りで複数入る。**レビュー済みのコミットが
軒並み「未レビュー」に見える**という、このツールの信頼を落とす一番まずい壊れ方をした
（レビューで指摘されて気づいた）。

書く側の形式は、読む側を書く前に**実物を見る**。

## CI

### サードパーティのactionは落ちる。標準で足りるなら使わない

CIの最初の実行が、テストを1つも動かさないまま両ジョブとも落ちた。原因は
`pnpm/action-setup` のダウンロードが **429 Too Many Requests**（3回リトライして力尽きる）。
自分のコードは1行も関係していない。

再実行すれば通っただろうが、**同じ落とし穴がそのまま残る**ので `corepack` に替えた
（Nodeに同梱なのでダウンロードが無い。しかもバージョンは `package.json` の
`packageManager` から取るので、workflow側との二重管理も消えた）。

CIの前段（action取得・依存インストール）は自分の管理外で落ちる。
**外せる外部依存は外す**——リトライで済ませると、次に同じ場所で止まる。

## 書き足すルール

- **足すのは「一度やらかしたこと」だけ。** 予防的な心得は書かない。増えるほど読まれなくなる
- 自動レビューが **FAIL** を出したら、直したあとにここへ1項目足す。
  コードの落とし穴（この関数はこう呼ぶ、この順序で書く）なら `CLAUDE.md` の方へ
- **何が起きたか**を具体的に書く。「〜に注意」だけの項目は、次に読んだとき判断に使えない
- 同じ話が2箇所に増えたら統合する。このファイルは長さではなく**読まれることが価値**
- 8KBを超えたらセッション開始時に警告が出る。出たら古い項目を畳む
