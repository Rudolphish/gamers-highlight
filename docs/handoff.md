### #33 のマージで分かったこと

`loading.tsx` を入れたことで、**権限が無いページのHTTPステータスが404から200に変わった**。
ストリーミングが始まると本文より先にヘッダーが出るため、後から `notFound()` しても
ステータスを変えられない（本文は正しくnot-found画面になるので**中身は漏れない**）。

権限の確認は**ステータスではなく本文で見ること**。詳細は `CLAUDE.md` の
「`loading.tsx` があると notFound() でも200が返る」。

### 引っかかるが「触らない」と決めたもの

- `next.config.js` の `outputFileTracingRoot` が**トップレベルにあるためNext.js 14では無視される**
  （起動時に `Unrecognized key(s) in object: 'outputFileTracingRoot'` が出る。14では
  `experimental` の下が正しい）。**#52 で調べた上で「触らない」と決めた。**
  無視されたままで意図どおりに動いている（`.next/standalone` に `packages/db` も入っている）ため、
  `experimental` の下へ移すと**このプロジェクトで初めてこの設定が有効になる**——良くて現状維持、
  悪くてデプロイ成果物が変わり、しかもVercelは自前のビルド出力を使うのでローカルで確認できない。
  判断の全文は `next.config.js` のコメントにある。**Next.js 15 に上げるときだけ注意**
  （上げた瞬間にこの行が有効になる）。

### その前に入れたもの（2026-09-02）：Botが落ちていた間の遡り取り込み

Botはローカル常駐なので普通に落ちる（PCの再起動・スリープ・デプロイ）。`messageCreate` は
Gatewayに繋がっている間しか届かないため、**落ちていた間の投稿は永久に取り込まれず、
取りこぼしたこと自体もどこにも残らない**（誰も気づけない）。

起動時に、落ちていた間のメッセージを遡って取り込むようにした（`apps/bot/src/lib/catchUp.ts`）。

- **起点は「最後の生存報告」。** 新しいテーブルは作らず、`BotHeartbeat.lastSeenAt`
  （15分おきに更新している）を使う。起動時の heartbeat が**更新前の値**を返すので、
  それが「自分が最後に生きていた時刻」になる
- **重複しない。** `discordMessageId`（`<メッセージID>:<添付ID>`）が一意なので、
  多めに舐めても既存ぶんはWeb側が弾く
- **上限**: 遡りは7日で打ち切り、1チャンネルにつき最大3ページ（300件）
- **「どのゲーム？」は聞かない。** 過去の投稿に今さら質問が並ぶとうるさいので、
  決まらなかったぶんは未分類のまま残す（アプリの「未分類の投稿」から振り分ける）
- 前回の生存報告が無い（初回起動）ときは**遡らない**

**Botのコードに初めてテストが付いた。** Discordには繋がず、偽のクライアントを渡して
取り込みの経路だけを本物で通している（F134〜F139）。そのためCIに
`pnpm --filter bot build` のステップを足した。

**Bot の再起動が要る。** 反映されるのは次に起動したときから。

### その前に直したもの（2026-09-02）：投稿してもアルバムが更新順で上がらない

ユーザー報告「グループ内のアルバムを更新順にしても、そのアルバムに投稿したものが上に来ない」。

**原因は2段構え。**

1. `Album.updatedAt`（Prismaの `@updatedAt`）は**アルバムの行を更新したときしか動かない**。
   写真を作っても増えるのは `Photo` の行だけなので、投稿では動かなかった
2. 唯一それらしく更新していた `photos/assign-album` も、**実は何もしていなかった**——
   `update({ data: {} })` は書く列が無いとUDPATE自体を発行しない（実測）。
   エラーも出ないので、コメントだけが「更新している」と言い続けていた

いまは `lib/albumTouch.ts` の `touchAlbum()` に寄せて、**写真がアルバムに入る4経路すべて**
（手動アップロード・Discord取り込み・`/tag`・Botの振り分け）で更新する。
**出ていく側では更新しない**（消したら上に来るのは直感に反するため）。

**並び順だけの問題ではなかった。** グループ画面は `updatedAt` の降順で上位N件しか読まないので、
更新されないアルバムは投稿が続いていても初期表示の窓から落ちていた。

過去ぶんは `pnpm --filter @gamers-highlight/db backfill:album-updated`（**既定は下見。
`-- --apply` で実行**）で埋められる。**まだ本番では流していない。**

### その前に入れたもの（#61〜#66）：活動ログ一式

`ActivityLog` / `DailyActivity` を土台に、**週次まとめ**と**カレンダー／タイムライン**を入れた。
設計の全文と「なぜその形か」は [`docs/activity-log.md`](./activity-log.md)。

- **土台（#61・#62）** — 出来事を記録する2つのテーブルと `logActivity()`。
  **時刻を2つ持つ**（`occurredAt`＝実際に起きた日時／`createdAt`＝記録時刻）のがこの設計の要で、
  週次まとめは後者、カレンダーは前者で並べる。記録漏れはCIの `audit-activity-log.mjs` が見る。
  既存データの遡り投入と、外部キーを張らない判断（張ると削除の記録ごと消える）も同時に入れた
- **週次まとめの画面（#63）** — `/admin/weekly`。グループ×週を選び、**Discordに送る文面をそのまま**
  プレビューする。cronは週1回しか動かないので、画面が無いと文面の調整に1週間かかる
- **日次ロールアップと保持期間（#64）** — 生ログは1年で消し、件数は `DailyActivity` に永久に残す。
  日次cron（`check-bot-health`）に相乗り。**集計してから消す**順序と、二重に走っても倍にならない
  （足し込みではなく置き換え）作りにしてある
- **Discordへの週次通知（#65）** — 曜日では判定せず「**最後に送った週**より新しい完了週があれば送る」。
  cronが数日飛んでも取りこぼさず、二度は送らない。**投稿に失敗したら記録を進めない**
  （後追いレビューの指摘。進めるとBotのkickや障害でその週が永久に失われる）
- **活動カレンダー（#66）** — `/admin/activity`。月カレンダー（日ごとの濃淡）＋タイムライン。
  **件数の出どころを日によって変えている**（1年以内は生ログ、それより古い日はロールアップ）。
  ロールアップだけを見ると、日次cronがまだ走っていない今日ぶんが必ず0に見えるため

**週次まとめもカレンダーも、いまは管理者タブだけに出している**（見せ方が固まってから
グループへ広げる、というユーザー判断）。`lib/weeklySummary.ts` と `lib/activityFeed.ts` は
権限を判定しないので、広げるときはページ側で `hasGroupPermission` を通してから呼ぶ。

### 招待リンク（#19）

グループ画面から発行するリンク。未登録の相手でもDiscordログインだけで
「許可リスト登録＋グループ加入」まで通る。有効期限・使用回数の上限・取り消しは必須要件。

**設計上いちばん重要な点**: 回数の消費は**グループ加入時ではなくログイン時**。
`AllowlistEntry` を作る＝アプリへの恒久的なログイン権限を渡すことなので、そこで数えないと
「1回限り」のリンクで複数人がログインできてしまう（詳細は `CLAUDE.md` の「権限」）。

### スクショからのゲーム自動判別（#21〜#26）

ファイル名から Steam の app ID を読んでタグとアルバムを決める。

**ファイル名の形は保存元で3通りあり、ゲームが分かるのはDL形式だけ**（`CLAUDE.md` 参照）。
普段の使い方（クリップボード貼り付け）では手掛かりが残らないため、

## 6. セッションの作り方（gitが使えない場合はここ）

git 操作ができるのは、**claude.ai/code からリポジトリを指定して作ったセッション**だけ。
その場合だけ次が自動で用意される。

- リポジトリのクローンと、**プロキシ経由のgit認証**（`HTTPS_PROXY` が経路上でトークンを差し込む。
  `GITHUB_TOKEN=proxy-injected` となっており、トークンの実体はどこにも置かれていない）
- GitHub MCP ツール（PRの作成・マージ）
- コミット署名鍵

**リポジトリを指定し忘れて作ったセッションでも、後から追加できる。**
ただし「追加して」だけだと**何に追加するのか伝わらず聞き返される**ので、こう頼む。

> `add_repo` で `owner=Rudolphish` `repo=gamers-highlight` を `access=push` で追加して、
> 案内されたコマンドでクローンし、`register_repo_root` まで済ませて。

- **`access=push` を明示する。** 既定は `read` で、取得はできても**pushとPR作成ができない**
- `add_repo` は登録するだけなので、**クローンは別に実行する**必要がある
- **`register_repo_root` を忘れない。** 呼ばないと `CLAUDE.md` が読み込まれず、
  ここに書いた落とし穴の知識が効かない

「そんなツールは無い」と言われたら、そのセッションはリモート実行環境ではない。
claude.ai/code からリポジトリを選択して作り直す。

ローカルCLI（自分のPCの `claude`）はこの仕組みを持たない。素直に `gh auth login` か
SSH鍵で認証する。真似る必要は無い。

切り分けるときは次を見る。

```bash
git remote -v
env | grep -i https_proxy      # 空ならプロキシが無い＝この仕組みの外
git ls-remote origin | head -3 # 認証が通っているか
```

## 7. 開発環境の再現

サンドボックスに本番のDBは無いので、**ローカルにPostgresを立てて検証している**。
次のセッションでも同じ手が使える。

```bash
# 既にあるデータディレクトリを起動する（ghdata / ghdata2 のどちらかが残っている）
ls /var/lib/postgresql/
setsid su postgres -c "/usr/lib/postgresql/16/bin/pg_ctl -D /var/lib/postgresql/ghdata2 \
  -o '-p 5433 -k /tmp' -l /tmp/pg.log start"
su postgres -c "psql -p 5433 -h /tmp -U postgres -d gh -c '\dt'"   # テーブルがあるか確認

# 接続先
DATABASE_URL="postgresql://postgres@localhost:5433/gh?host=/tmp"
```

**セッションを跨ぐとPostgresは動いていない。** コンテナが作り直されるとプロセスは落ちており、
データごと消えていることもある（実際に一度消えた）。`\dt` でテーブルが出なければ
`tools/local-test/README.md` の手順1から作り直す（`initdb` → `CREATE DATABASE gh` →
`prisma migrate diff` の出力を `psql` に流す）。**`.env` は読み込まれない**ので、
スクリプトを流す前に `set -a; . ./apps/web/.env.local; set +a` を通すこと。

- **`prisma db push` は権限で失敗する**ので、スキーマ変更は
  `prisma migrate diff` の出力を `psql` に流して当てている
- 本番ビルドで確認する（`next build && next start`）。`dev` だとNext.js自身の
  エラーオーバーレイが出て、アプリのエラーバウンダリの挙動を確認できない
- ログインは `dev-login` が本番ビルドで無効なため、**NextAuthのJWTを直接発行**して
  Cookieに入れている（`NEXTAUTH_SECRET` を合わせるだけ）。トークンは1時間で切れるので、
  Playwrightで「0件」になったらまず再発行を疑う
- 外部APIは `globalThis.fetch` を差し替えて確認する。R2は「PUTは受けてPOSTには501を返す」
  模擬サーバーを立てると、本番と同じ壊れ方を再現できる

**この手順一式は [`tools/local-test/`](../tools/local-test/README.md) にある。**
シード・スタブ・模擬R2・権限マトリクスまで揃っているので、次からは手で組み直さなくてよい。

## 8. 進め方の約束

このリポジトリでの作業は次の形で回している。

1. **ブランチを切る**（`claude/<内容>`）。master に直接コミットしない
2. **バグは直す前に再現させる**。再現した証跡をPRの説明に載せる
3. PRの説明には**判断の理由と、確認できなかったこと**を書く
4. マージはユーザーの指示を待つ
5. スキーマを変えたら、PRに **`prisma db push` が必要**と明記する
   （Vercelはコードしかデプロイしないため）
6. **マージ前に全件は流さない。** 変更に関係するスイートだけを流す。
   全件はCI（`.github/workflows/ci.yml`）がPRで流すので、手元で回す必要は無い
   （`tools/local-test/` は個別に実行できる。`docs/test-results.md` には
   スイートごとの実行時刻が入るので、どこが古いかは表を見れば分かる）
7. **マージ前にレビュー済みか確認する**（下記）

### セッションを跨いだ学び

`docs/lessons.md` に「**進め方でやらかしたこと**」を残している。
`CLAUDE.md`（コードの落とし穴）とは別。確認の仕方・道具の使い方・判断の順序など、
コードを読んでも分からないぶん。セッション開始時に `session-brief.mjs` が全文を出す。

書き足す経路は2つ:

- 自動レビューがFAILを出すと、修正指示と一緒に「学びを1項目足すこと」が渡される
- 気づいたときに自分で足す（ルールはファイル末尾の「書き足すルール」）

**手で書きに行く前提のファイルは風化する。** `.claude/hooks/review-decisions.csv` は
まさにそれで、作った日から1行も増えていない。だからFAILの経路に指示を埋め込んである。

### 自動レビューの確認方法

Stopフック（`.claude/hooks/auto-review.mjs`）が別プロセスの `claude -p` にレビューさせ、
結果を `.claude/hooks/review-ledger.csv` と `docs/review-log/` に残す。
**このフックは黙って走るので、「PASSした」のか「そもそも走らなかった」のかは
自分からは見えない。** マージ前に必ずこれで確認すること。

```bash
node .claude/hooks/review-status.mjs          # HEADの状態
node .claude/hooks/review-status.mjs --range  # このブランチで足したコミット全部
```

`--range` の起点は**既定ブランチとの分岐点**（＝マージされる中身と同じ範囲）。
セッション開始地点ではない。確認したいのはマージ直前で、その時点ではフックが
起点をHEADまで進め終えており、それを見ても「対象コミットがありません」としか出ないため。

終了コード 0=PASS / 1=未レビュー / 2=指摘あり。表示は3種類:

| 表示 | 意味 |
|---|---|
| `✓ PASS` | レビュー済み・問題なし |
| `✗ 未レビュー（台帳に記録がありません）` | 一度も対象になっていない |
| `✗ 未レビュー（見送り: 理由）` | 対象にはなったがレビューせず飛ばした |

飛ばされていた分は後から掛け直せる。

```bash
node .claude/hooks/auto-review.mjs --range <sha>          # そのコミット1件
node .claude/hooks/auto-review.mjs --range <from>..<to>   # 範囲
```

**過去に、新しいブランチの最初のコミットが必ず飛ばされていた。**
squashマージ後に `origin/master` からブランチを切り直すと、前回の起点が
新しいHEADの祖先でなくなる。当時のフックはこれを「追えない」として
レビューせず起点だけ引き直しており、しかも台帳にも残していなかった。
実測で10ブランチ中9本の初回コミットが該当し、うち6本はブランチ全体が未レビューのまま
マージされていた（#40・#41・#45・#46・#47・#48）。
今は既定ブランチとの分岐点を代わりの起点にするので範囲はPRの中身と一致し、
それでも見送る場合は台帳に `SKIP` 行が理由つきで残る。

**master 上のコミットは常に「未レビュー」と出る。** squashマージで新しいSHAが
振られるため、台帳（ブランチ上のSHAで記録されている）と一致しない。
確認するのはマージ前のブランチ上であって、master に対して流す意味は無い。
