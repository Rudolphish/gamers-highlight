## 1. 何を数えるか（この設計の要）

**記録するのは個人のプレイ時間ではなく「グループとして一緒に遊んだ時間」。**

> グループのDiscordサーバーの**同じボイスチャンネル**に、**同じゲームを「プレイ中」**にしている
> **対象メンバーが2人以上**いる間を、1回のグループプレイとして数える。

壁打ちの途中まで、私（Claude）は「各自のプレイ時間をグループに見せる」と取り違えて
設計を進めていた。ユーザーの意図は「**このグループはこれだけ遊んだ**」。
個人単位の前提で決めた項目は、グループの記録に当てはめ直して確認を取ってある（§2）。

- **VCが条件に入っているのは「一緒に遊んだ」に一番近いから。** 「2人以上が同時に同じゲーム」
  だけだと、別々にソロで遊んでいただけでも数えてしまう
- ~~**ゲーム中が1人だけなら数えない。**~~ → **2026-10-11 に変更：プレイ中が見えない対象者も、
  そのVCで見えているゲームが1つだけなら組に数える**（ユーザー判断）。
  Discordで「オンライン状態を隠す」にしている人は、Botからはオフライン・プレイ中なしにしか見えない
  （隠している本人の画面には「プレイ中」が出るので、本人は気づかない）。グループの4人中3人がこの設定で、
  最初に4人で遊んだ回は見えるのが1人だけになり、**記録が0件だった**。
  引き換えに、VCで雑談しているだけの人も「一緒に遊んだ」に入る。見えているゲームが2つ以上のVCでは、
  見えない人をどれに入れるか決められないので数えない（`apps/bot/src/lib/playLog.ts` の
  `computePlayingGroups`）
- **始まりと終わりはBotが自動で判断する。** 誰かがコマンドを打つ必要はない
  （条件が成り立ったら開く、崩れたら閉じる）

## 2. 決まっていること（2026-10-10 ユーザー判断）

### 対象と同意

- **最初から全員が対象。記録されたくない人は外れられる**（`/playlog off`）。
  グループ単位の有効化スイッチは作らない。**導入時にはグループへ一言告知する**こと
- **外れるのはコマンドを打ったグループだけ**（1グループ＝1 Discordサーバー）
- **外れた人の過去の記録はそのまま。** これからの人数判定にも参加者にも入らないだけ
  （過去の記録は「グループで遊んだ事実」なので消さない）
- **アプリ未登録・Discord未連携の人は、人数にも参加者にも入れず、名前も残さない。**
  アプリに同意していない人の情報を持たないため。Botのメモリ上で捨て、Webへは送らない
- 誰の記録かは `User.discordUserId`（設定 → Discord で紐づける）で決める

### 記録の扱い

- **5分未満のプレイも保存する。表示では5分未満を出さない**（合計時間には含める）。
  データを捨てないので、あとでしきい値を変えても過去分に効く
- **途切れが10分以内なら1回にまとめる。** 誰かのクラッシュで一時的に1人になった、等
- **Botが落ちていた間に終わった記録は、最後に生きていた時刻で閉じて「推定」の印を付ける。**
  少なめに数える側に倒す。復帰時に同じゲームがまだ続いていれば、そのまま続きとしてつなぐ
- **途中の記録はWebのDBに「終了時刻が空」で持つ。** Botのメモリだけに持つと、落ちた瞬間に
  途中のプレイが痕跡もなく消える。ホームの「今プレイ中」もこの行から出せる

### ゲームの対応付け（3段）

1. **DiscordのアプリIDで当てる。** 一度対応が分かったら「DiscordアプリID→Steam appId」を保存し、
   次からはこれで当てる
2. **名前で当てる。** Discordの表示名を、グループのゲームリストの**日本語名と英語名の両方**と照らす
   （`GroupGame.title` は日本語名。`CLAUDE.md`「Steam の検索は日本語名を返す」）
3. **当たらなければ名前だけで記録し、グループのメンバーが1回選ぶ。** 選んだ結果は1段目の対応として
   保存し、同じアプリID／名前の過去の記録にも反映する

- **共有されたアプリID（19桁）はDiscord側のID。Steamの番号ではない。** 初回はSteamと直接
  結びつかないので、2段目→保存→次から1段目、という流れになる
- **Discordが非公式に持つSteamの情報（SKU）は当てにしない**
- **ゲームリストに無いゲームも名前だけ記録しておく。** あとでリストに足したら過去分も結びつく
- **選ぶのはグループのメンバーなら誰でも**（いまの「未分類の投稿」と同じ考え方）。
  選ぶ場所は**アプリの画面**（Discordには何も投稿しない。遊んでいる最中に邪魔をしないため）

### 表示

- 表示先は4つ：**ゲーム詳細**（グループの合計・直近の記録・参加者）、**週次まとめ**
  （今週よく遊んだゲーム）、**活動カレンダー／タイムライン**、**ホームの「最近遊んだ」**
- **参加者を出す**（「10/10 21:00〜23:30 Dying Light（A・B・C）」）。思い出としては
  誰と遊んだかが大事なので
- 公開範囲はグループ内

### コマンド

- `/playlog`（日本語のDiscordでは「プレイ記録」と表示。`name_localizations`）。
  英字にしたのは、入力中にIMEを切り替えなくて済むようにするためと、既存の `/tag` に揃えるため
- サブコマンドは `on` / `off` / `status`。返信は本人にだけ見える形（ephemeral）
- 未連携の人が打ったら、断って連携画面（`/settings/discord`）へ案内する
- `status` は**いまBotからどう見えているか**も返す（2026-10-11 追加）。打った人と同じVCにいる人ごとに
  「プレイ中のゲーム名とアプリIDの有無／プレイ中が届いていない／対象外」、いま記録される組、
  対象者の数、Webへの最後の送信の成否と失敗理由。対象外の人のゲームは出さない

**記録が付かないときは、遊んでいる最中に `/playlog status` を打つ。** 4人で遊んだのに記録が0件
だったとき、原因の候補（①プレイ中がBotに届いていない＝Discordのアクティビティの共有がオフ、
②同じゲームのアプリIDが人によって違い1人ずつに分かれた、③送ったがWebに弾かれた）を
外から区別できなかった。**送れたときに何も残さない作りだった**ため（Botのログも失敗しか出さず、
そのPCを落とすと見られない）。いまは送れたときも `[playlog] guild=... 送信: N組` を1行出す。

### 最少人数の切り替え（2026-10-14 追加・ユーザー判断）

記録の最少人数は既定2人。**管理者（`ADMIN_EMAILS`）だけ**がグループ画面で「1人（動作確認用）」に切り替えられる。
1人用のテストグループで実際の動き（記録・通知・表示）を確かめるためのもの。オーナーに開けていないのは、
友人のグループで誤って1人にすると「一緒に遊んだ時間」にソロプレイが混ざるため。

- 値は `AppSetting` の `playLogMinParticipants:<groupId>`（"1" のときだけ行がある）。本番DBの変更は要らない
- Webの判定（スナップショットの反映）は即時。Botは対象者の一覧と一緒に取るので、**届くまで最大15分**
  （誰かが `/playlog` を打てばその場で取り直す）。`/playlog status` に最少人数が出る
- 1人でも「同じVCにいること」は条件のまま（VCに入らずに遊んでも記録されない）

### 通知（2026-10-11 追加・ユーザー判断）

グループの通知設定の種類「**プレイ記録の開始と終了**」（`GroupNotificationKind.PLAY_LOG`）に
チャンネルを選ぶと、そこへ送る。**行が無いグループには送らない**（他の種類と同じ）。中身は `lib/playLogNotify.ts`。

- **開始**：行を作った瞬間に「🎮 〇〇 の記録を始めました／参加: …」。つなぎ直し（10分以内に戻った・
  Botの再起動）では送らない。送れなかったら送り直さない（遅れて届く「開始」に意味が無いため）
- **終了**：**閉じてから10分戻らなかった行だけ**「🏁 〇〇 を 1時間20分 遊びました／参加: …」。
  閉じた直後に送ると、一瞬落ちて戻っただけの回にも「終わった」が出て、続きの「開始」は出ない。
  拾うのはスナップショットと**15分おきの生存報告**（変化が無ければBotはスナップショットを送らないので）。
  なので実際に届くのは終わってから10〜25分後
- **長く落ちていた後の最初の生存報告では終了を送らない。** Botが落ちている間に閉じた行は、直後の起動処理で
  「続き」としてつなぎ直されうる。先に「終わった」を出すと嘘になる
- **送れなかった終了は印（`endNotifiedAt`）を外して次で送り直す**（「送ったことにして進める」と、
  Discordが落ちていた回の通知が永久に消える。`CLAUDE.md` の週次まとめの件と同じ）。6時間より前に
  終わった行は送らない（列を足した時点の過去の行や、長く送れなかった行をまとめて流さないため）
- 送り先が無いグループの行も印だけ付ける。**後からチャンネルを設定しても過去の回は送らない**

## 3. 前提（コードと実機で確認したこと）

- **Botはローカル常駐のプロセス。** Botを動かしているPCが寝ている間は、プレイの開始も終了も
  一切届かない。**Discordには過去のプレイ状況を後から取りに行く手段が無い**ので、画像の取り込み
  のような遡り（`apps/bot/src/lib/catchUp.ts`）はできない。**記録の網羅性はBotの稼働時間で決まる**
- **最後に生きていた時刻は既にある。** `BotHeartbeat.lastSeenAt` が15分おきに更新され、
  起動時の heartbeat は**更新前の値**を返す（遡り取り込みと同じ仕組みを使える）
- **プレイ状況の通知は頻繁に来る。** ゲーム内の場面が変わるだけでも届く（リッチプレゼンスの
  `details` / `state` の変化）。**Botの側で「ゲームが変わった・VCの顔ぶれが変わった」ときだけに
  絞ってWebへ送る**
- **Discordのアクティビティ**: `name`、任意の `application_id`（Discord側のID）、任意の
  `timestamps`。Steamの番号を持つ欄は `discord-api-types` に無い。数えるのは `type` が
  Playing（0）のものだけ（Spotify・カスタムステータス等を除く）
- 既存の Intents は `Guilds` / `GuildMessages` / `MessageContent`。
  **足すのは `GuildPresences`（特権）と `GuildVoiceStates`（特権ではない）**

## 4. テーブル（案）

名前と列は実装時に詰める。決まっているのは「何を持つか」。

```prisma
/// グループとして一緒に遊んだ1回。endedAt が null なら進行中
model GroupPlaySession {
  id                   String    @id @default(cuid())
  groupId              String
  groupGameId          String?   // 3段で当たらなければ null（名前だけで記録）
  discordApplicationId String?   // アクティビティに付いていれば
  activityName         String    // Discordの表示名（当たらなかったときの手掛かり・後からの照合用）
  voiceChannelId       String
  startedAt            DateTime
  endedAt              DateTime?
  endEstimated         Boolean   @default(false) // Bot停止中に終わった＝最後に生きていた時刻で閉じた
  participants         GroupPlayParticipant[]
}

/// 参加者。外れた人も過去の行は残す（§2）
model GroupPlayParticipant {
  sessionId String
  userId    String
  joinedAt  DateTime
  leftAt    DateTime?
  @@id([sessionId, userId])
}

/// 1段目の対応。グループをまたいで共通（Discordのアプリとsteamの対応はグループに依らない）
model DiscordAppSteamMapping {
  discordApplicationId String @id
  steamAppId           Int
  createdById          String?
  createdAt            DateTime @default(now())
}

/// 外れた人。行がある＝そのグループでは数えない
model PlayLogOptOut {
  groupId   String
  userId    String
  createdAt DateTime @default(now())
  @@id([groupId, userId])
}
```

- **英語名はどこにも保存されていない**（`getSteamAppSummary` で取れるが、使っているのは
  ジャンルと画像だけ）。2段目のために `ExternalGameCache` に英語名の列を足し、追加・リフレッシュ時に
  埋める。**既存のゲームには入っていない**ので、埋め直し（バックフィル）が要る
- 名前だけで記録した行に、アプリIDが付いていない場合もある。そのときの「過去分への反映」は
  `activityName` の完全一致で行う
- 活動ログ（`ActivityLog`）に「グループで遊んだ」を流すかは M2/M3 で決める。
  M1 はこのテーブルだけで完結させる

## 5. 検知と送り方

**Botは「いまの状態のスナップショット」をWebへ送り、Webが行の開閉を決める。**
「始まった」「終わった」のイベントを送る形にしないのは、1件取りこぼすと開きっぱなし／
閉じっぱなしになるため。スナップショットなら次に送った時点で辻褄が合う（冪等）。

### Bot側

1. 対象者の一覧（連携済み・外れていない人の Discord ユーザーID）を、グループごとに
   Webから取ってメモリに持つ。起動時と `/playlog` 実行時と、一定間隔で取り直す
2. `voiceStateUpdate` と `presenceUpdate` を受けたら、そのサーバーについて
   「VCごと・ゲームごとに、対象者のうち誰が遊んでいるか」を計算し直す
   （**ここは純粋関数にしてテストする**）
3. 計算結果が前回と変わったときだけ、そのサーバーのスナップショットを送る
4. 対象外の人のプレイ状況はメモリ上で捨てる（Webへは送らない）

ゲームの同一性は `application_id` があればそれ、無ければ `name` で見る。

### Web側

- スナップショットに無い進行中の行 → 閉じる（ただし10分は「閉じかけ」で保持し、
  その間に同じグループ・同じゲームが戻ってきたら同じ行を続ける）
- スナップショットにあって進行中の行が無い → 開く（ここで3段の対応付けをする）
- 参加者の出入りを `GroupPlayParticipant` に反映する

### Botが落ちていた間

- 起動時、heartbeat が返す「前回生きていた時刻」で、そのグループの進行中の行を
  **閉じて `endEstimated` を立てる**
- 直後に送る最初のスナップショットで、同じゲームがまだ続いていれば**閉じた行を開き直して続きとする**
  （閉じたままにすると、Botの再起動のたびに記録が2つに割れる）

## 6. M1 の範囲

- 記録の取り込み一式（§4 のテーブル・§5 の検知・`/playlog on|off|status`）
- **ゲーム詳細ページ**に「グループで遊んだ時間」の区画：合計時間・直近10件程度
  （日時・長さ・参加者・「推定」の印）。**記録の正しさを1画面で確かめるための段階**
- **グループ画面に「ゲームが分からないプレイ」**と、そこから選ぶ導線（3段目）
- 区画は `Promise.allSettled` でセクション単位に失敗させる（`CLAUDE.md`「外部依存は
  セクション単位で失敗させる」）。ページ側で `hasGroupPermission` を通す

M2（ホーム・週次まとめ）、M3（活動カレンダーのグループ公開）は M1 の記録を実データで
見てから詰める。

## 7. 入れる順序（ここを間違えるとBotが起動しなくなる）

1. **ユーザーが開発者ポータルで Presence Intent を有効にする**
2. その後で `GuildPresences` を要求するBotをデプロイする

特権Intentを、ポータルで許可しないままコードで要求すると、Discordは接続を拒否する
（Gatewayのクローズコード 4014 "Disallowed intent(s)"）。**Botが起動しなくなり、画像の取り込みも
止まる**。この挙動は Discord の仕様として知られているもので、このリポジトリではまだ実測していない。

あわせて `deploy-commands.ts` で `/playlog` の登録が要る。

## 8. 確かめ方

- **CIからDiscordには繋がらない。** だから検知は「VCの状態＋プレイ状況＋対象者 → 遊んでいる組」の
  純粋関数に切り出して単体で確かめる
- Web側はスナップショットを偽装して `flows` で流す：開く・閉じる・10分以内の再開で同じ行・
  Bot停止からの復帰（推定で閉じる→続いていれば開き直す）・外れた人が数に入らない・
  未連携の人が送られても無視される・3段目で選んだら過去分に反映される
- **最後は実機。** 2人以上で同じVCに入って同じゲームを遊ぶ。途中で1人抜けて10分以内に戻る、
  Botを止めて再開する、も見る

| `apps/web/src/app/api/cron/check-bot-health` | Botが落ちていたら、進行中の行を最後に生きていた時刻で閉じる |
| `apps/bot/src/lib/playLog.ts` | 検知の純粋関数（VC＋プレイ状況＋対象者 → 遊んでいる組） |
| `apps/bot/src/lib/playTracker.ts` | Discordのイベントを受けて、変わったときだけスナップショットを送る |
| `apps/web/src/lib/playLogNotify.ts` | 開始・終了の通知（種類 `PLAY_LOG`）。スナップショットと生存報告のAPIから呼ぶ |
| `apps/bot/src/commands/playlog.ts` | `/playlog on|off|status`（日本語表示「プレイ記録」）。`status` はBotからの見え方も返す（文字の組み立ては `lib/playLog.ts` の `describePlayStatus`） |

### 実装で決めたこと（設計書に無かったもの）

- **起動直後のつなぎ直しは、Discordのアクティビティの開始時刻で判断する。** 参加者のうち**1人以上**の
  開始時刻が「前回生きていた時刻」より前なら、落ちる前から遊び続けていたとみなして閉じた行をつなぐ
  （2026-10-11 に2人以上から変更。見えない人を数えるようにしたので、開始時刻が分かるのが1人だけの組が普通にある）。
  開始時刻が無い（ゲームが送ってこない）ときはつながない。そうしないと、一晩Botが落ちていた間を
  まるごと「遊んでいた」にしてしまう
- **人数の条件と対象者の絞り込みはWebでももう一度かける。** Botの対象者一覧は15分おきにしか
  取り直さないので、外れた直後でも数えないように
- **英語名は追加・リフレッシュ時に `ExternalGameCache` へ入る。** それより前のゲームは、
  照合のときに1回あたり10本まで appdetails を引いて埋める（取れなかったものは保存しない）
- **名前だけで記録したものは、グループ画面を開いたときに1段目・2段目で当て直す。** ゲームを足す経路が
  複数あるので、足す側ではなく見る側で拾う
- **進行中の行は、Botの生存報告が35分以上途絶えていたら最後に生きていた時刻で切って出す**
  （日次cronが閉じるまでの間、何日も「プレイ中」と出し続けないため）
- 合計は時間の和集合（同じゲームを別々のVCで同時に遊んでいても二重に数えない。§9 の1つ目）

### 本番に入れる手順（順序どおりに）

1. スキーマを本番へ反映する。追加だけなので既存データには触らない。2通りある:
   - **Supabaseのコネクタ経由**（2026-10-11 ユーザー判断でこちらに寄せる）：master の
     `schema.prisma` → このブランチの `schema.prisma` の差分SQLを作り、ユーザーに見せてから
     `apply_migration` で流す。本番の接続情報をクラウド環境に置かずに済む。
     差分SQLは `npx prisma migrate diff --from-schema-datamodel <master の schema.prisma>
     --to-schema-datamodel packages/db/schema.prisma --script` で作る（**流す前に `list_tables` で
     本番が master と同じ形か＝新しいテーブルがまだ無いかを確かめる**）
   - ユーザーの手元で `pnpm --filter @gamers-highlight/db exec prisma db push`
     （**ローカルが最新か確認してから**）
2. Webのデプロイ（PRのマージで自動）
3. Botの入れ替え：`pnpm --filter bot pm2:restart`
4. コマンドの登録：`pnpm --filter bot deploy-commands`（`/playlog` が出るようになる）
5. グループに一言告知する（最初から全員が対象のため。外れるのは `/playlog off`）

1 より先に 2 を入れると、ゲーム詳細とグループ画面が**テーブルが無いエラーで区画ごと出なくなる**
（ページ自体は落とさない作りにしてある）。3 より先に 2 が要るのは、Botが新しい内部APIを叩くため

## 11. M3 の計画：活動カレンダーにプレイ記録を載せ、グループ向けに公開する（2026-10-15 ユーザー判断）

きっかけは「活動カレンダーにゲームをプレイした記録も載せたい。最終的にはグループ単位でみんなが閲覧できるようにしたい」。
2026-10-15 時点で本番のプレイ記録は1件（テストグループの Timberborn、約1時間26分）だけで、
**2人以上で遊んだ実データはまだ無い**。

### 進め方：2段階（ユーザー判断）

| 段階 | 中身 | 見る人 |
|---|---|---|
| 1 | 管理画面のカレンダー（`/admin/activity`）にプレイ記録を載せ、見た目を確かめる | 管理者 |
| 2 | グループ用の活動ページを作り、メンバー全員が見られるようにする | グループのメンバー（閲覧者以上） |

PRも分ける。段階1で見た目を確かめてから公開する（`docs/activity-log.md` §9-4「まず管理者タブにだけ出す」と同じ考え方）。

### 段階1で決めたこと

- **`ActivityLog` に写さず、`GroupPlaySession` を直接読む。** 写すと、10分以内に戻ってつなぎ直した回・
  Botの再起動をまたいだ回・後からゲームを結びつけ直した回で、ログと記録がずれる（`targetName` は写した時点の名前で固まる）。
  プレイ記録は消さずに永久に残すので、生ログの1年の保持（古い日は件数しか出ない）にも引っかからない
- **日のマスには「🎮＋その日の合計時間」を出す**（ユーザー判断）。出来事の件数には混ぜず、濃淡も今までどおり件数で付ける。
  「1回＝1件」で数えると、10分と5時間が同じ重みになる
- **日付をまたいだ回は、始まった日（JST）にまとめて載せる。** 夜中に遊んだ回が2日に割れると、
  1回の思い出が2つに見える。合計時間は `lib/playLog.ts` の和集合の考え方（同じゲームを別々のVCで同時に遊んでいた
  時間を二重に数えない）に揃える
- **タイムラインには1回1行で混ぜる**（「🎮 Timberborn を 1時間26分（A・B）」、始まった時刻で並べる）。
  終わりが推定の回はそう添える。進行中の回は「遊んでいる」として出す
- ゲーム名は結びついていればゲームリストの名前、無ければ Discord の表示名（`activityName`）。結びついていればゲーム詳細へリンクする

### 段階2で決めたこと

- **置き場所は専用ページ**（`/groups/[groupId]/activity`。ユーザー判断）。グループ画面から「活動カレンダー」のリンクで開く
- **ページ側で `hasGroupPermission(…, "VIEWER")` を確かめ、無ければ `notFound()`**（`CLAUDE.md`「ページはAPIの権限判定を通らない」）。
  配下に `loading.tsx` があるので権限が無くても200で返る。テストは本文で見る（`CLAUDE.md`）
- **取り消し系の出来事はグループには出さない**（ユーザー判断）。写真の削除・❤️の取り消し・投票の取り消し・
  説明を消した・提案の取り下げは管理画面だけに出す。件数（マスの濃淡）からも外す
- **公開の前に直す：表示名が無い人をメールアドレスで出している**（`lib/activityFeed.ts` の `actor?.name ?? actor?.email`）。
  グループに見せると他のメンバーにメールが見えるので「メンバー」に置き換える（通知と同じ扱い。`lib/playLogNotify.ts`）
- 管理者向けのグループ切り替えは出さない（そのグループだけを見せる）
- テスト: 他グループの人・未ログインの人に中身が出ないこと、メールアドレスが出ないこと、取り消し系が出ないこと

- ホームに「最近遊んだ」を出す

## 12. 管理者がプレイ記録を直す（2026-10-17 ユーザー判断）

きっかけは、週末ゲーミングで遊んだ回が記録されなかった件（`/playlog` もそのサーバーに出ていなかった。
Bot の `.env` の `DISCORD_GUILD_ID` がテスト用サーバーを指していて、コマンドがそこにだけ登録されていた）。
「記録できたら（できなかったら）管理者権限で後から時間を直したい」。

- **できること：時間の修正・削除・記録されなかった回の手動追加**（ユーザー判断）
- **置き場所：管理画面 `/admin/play-log`**（ユーザー判断）。全グループの記録を新しい順に50件ずつ。グループで絞れる
- **直せるのは管理者だけ**（ユーザー判断。`isAdminEmail` をAPI側で必ず呼ぶ）
- 処理は `lib/playLogAdmin.ts`、API は `/api/admin/play-sessions`（POST）・`/api/admin/play-sessions/:id`（PATCH・DELETE）

### Bot の記録とぶつからないように決めたこと

- **進行中の行（`endedAt` が null）は直せない・消せない（409）。** Bot がまだ開け閉めしている
- **手で足した行の `gameKey` は `manual:<UUID>`、`voiceChannelId` は `manual`。** Bot の `gameKey`（`app:…` / `name:…`）と
  重ならないので、10分以内の再開や起動直後のつなぎ直しで Bot に拾われない。画面では「手動で追加」と出す
- **手で足した行・直した行に終了の通知を飛ばさない。** 通知は「閉じてから10分〜6時間で、まだ送っていない行」に送るので、
  足した時点・直した時点で `endNotifiedAt` を埋める（直す前に既に送ってあれば触らない）
- 手で足すときはゲームをゲームリストから選ぶ（名前だけの手動記録は作らない）。直すときは名前だけの記録のまま残すこともできる
- 直した行は「終わりは推定」を外す（人が確かめた値になる）
- 参加者を直すと入れ替える。残った人の入った・抜けた時刻は新しい範囲に収める
- 入力の確認：終了は開始より後・1回は24時間まで・終了は今より後にしない・参加者はそのグループのメンバー（オーナー含む）・
  ゲームはそのグループのゲームリストのもの。どれも理由を文章で返し、画面にそのまま出す
- 活動ログには流さない（プレイ記録はまだ活動ログに流していない。§4・§11）。キャッシュにも載っていないので無効化は要らない
- テスト: F293〜F296（追加・入力の確認・修正と進行中の扱い・削除と権限）、R58〜R60、P26d、B112（画面の配線）

## 13. グループ画面に合計プレイ時間、ゲーム一覧に各ゲームの時間を出す（計画。2026-10-17 ユーザー判断）

きっかけは「グループ画面のトップに全ゲームの合計プレイ時間を出したい。ゲーム一覧の各ゲームにもプレイ時間を出したい」。
**計画だけ**（実装はユーザーの都合のよいときに）。

### 決めたこと（ユーザー判断）

| 項目 | 決めたこと |
|---|---|
| 合計の数え方 | **各ゲームの時間を足す**。ゲーム一覧に出る時間の合計と必ず一致する。別々のVCで同時に別のゲームを遊んだ時間は両方数える |
| ゲームに結びついていない記録 | **合計に含めない**。結びつけた時点で合計に入る（「ゲームが分からないプレイ」の区画が結びつけを促している） |
| トップの見せ方 | **グループ画面の上の方に目立つ形で**。5つの見本（大きな数字のカード／合計＋内訳／タイル3つ／大きな帯／控えめなバッジ）から**「大きな帯」**を選んだ（2026-10-17）。グループ名と設定のすぐ下、アルバムの区画より上に、グループの看板として横いっぱいの帯を置く。中身は「グループで遊んだ時間」の大きな数字と、その下の1行（**いちばん遊んだゲーム**・**ゲームの本数**・**最後に遊んだ日**） |
| ゲーム一覧 | **各ゲームに「🎮 3時間20分」を出すだけ**。0分のゲームには出さない。並び替えは足さない |

### 作り方（案）

- **1ゲームぶんの数え方はゲーム詳細と同じにする。** 同じゲームを別々のVCで同時に遊んでいた時間は二重に数えない（和集合）。
  進行中の回は今までの分を数え、Botの生存報告が途絶えていたら最後に生きていた時刻で切る（`getGamePlaySummary` と同じ）。
  ゲーム詳細とグループ画面で数字が食い違わないよう、数え方は `lib/playLog.ts` の1つの関数に寄せる
  （`getGroupPlayTotals(groupId)` → ゲームごとの時間と合計。ゲーム詳細の合計もこれと同じ計算を通す）
- グループの記録をまとめて1回で引く（ゲームごとに引くと本番では本数ぶん往復する。`CLAUDE.md`「速度」）
- **キャッシュには載せない。** グループの中身は `unstable_cache`（`lib/groupData.ts`）に載っているが、プレイ記録は載せていない
  （Botの記録・管理者の修正のたびに無効化が要るのを避ける）。ページ側で別に引いて、部品に渡す
- 時間の文字（「3時間20分」）を作る関数は、いまサーバー側の `lib/playLogNotify.ts` にある。ゲーム一覧は画面側の部品なので、
  DBを読まない小さなファイルに移して両方から使う
- **グループ画面のDBクエリ数の上限（7。テストの Q05）を見直す。** 今は5回で、記録の取得と生存報告の確認で2回増える。
  上げるときは理由をテストのコメントに書く（黙って上げない）
- 帯の1行に出す3つは、合計と同じ1回の取得から作る（問い合わせを増やさない）。「いちばん遊んだゲーム」は時間が最も長いゲーム
  （同じ時間なら最後に遊んだ方）、「最後に遊んだ日」はゲームに結びついた記録のうち一番新しい日（進行中なら今日）
- 帯は目立つぶん、ほかの区画より強くなりすぎないか、実装後に実際の画面で確かめる（見本では背景を暗い青のグラデーションにした）
- 合計が0（記録が1件も無い）のグループでは、帯は出さない（これから使うグループで空の大きな枠が出ないように）

### テスト（案）

- 2つのゲームに記録を作り（同じゲームの重なった回・進行中の回・結びついていない回を含む）、グループ画面の合計と
  各ゲームの時間を見る。合計＝各ゲームの和、結びついていない回は入らない、ゲーム詳細の合計と一致する
- 実ブラウザで、帯（合計・いちばん遊んだゲーム・本数・最後に遊んだ日）とゲーム一覧の時間が出ること、0分のゲームに出ないこと、記録が0件のグループでは帯が出ないこと
- 壊し確認：和集合を外す・結びついていない回を混ぜる・ゲーム詳細と別の計算にする、でそれぞれ落ちること
