# 表示を速くする手段の検討（キャッシュ）

「一度開いたページの2回目を速くしたい」に対する調査。**実測してから順番を決める**ための資料。
骨格表示（#33）は「押した瞬間に画面が変わる」ための対策で、待ち時間そのものは減っていない。
ここで扱うのは待ち時間そのもの。

---

## 1. 実測

ローカルの本番ビルド（`next build && next start`）＋ローカルPostgres。
`tools/local-test/` の環境で測った。

### 一度開いたページに戻ったとき

実ブラウザ（Chromium）でリンクを踏んで行き来し、サーバーへの取得（RSC要求）を数えた。

| 操作 | サーバーへの取得 |
|---|---|
| 1回目 `/groups` → `/albums` | 1件 |
| 2回目 `/albums` → `/groups`（戻る） | **0件** |
| 3回目 `/groups` → `/albums`（再訪） | **0件**（周辺リンクの先読みのみ） |
| 35秒待ってから再訪 | 1件 |

**つまり「一度開いたページの2回目」は既に速い。ただし30秒だけ。**
Next.js 14.2 のクライアントルーターキャッシュ（`experimental.staleTimes`）の既定値が
`dynamic: 30`（秒）で、その間は再訪してもサーバーへ行かない。

この30秒は**そのタブのメモリ**なので、リロード・別タブ・別端末では効かない。

### ページごとのDBクエリ数

シードは2グループ・2アルバム・写真7件・ゲーム3件という**最小のデータ**での値。

| ページ | クエリ数 | ローカル所要 |
|---|---:|---:|
| `/groups/<id>` | **22** | 20ms |
| `/albums/<id>` | 12 | 25ms |
| `/albums` | 10 | 24ms |
| `/groups/<id>/games/<id>` | 9 | 16ms |
| `/admin` | 7 | 25ms |
| `/`（ホーム） | 5 | 29ms |
| `/albums/unclassified` | 4 | 24ms |
| `/groups` | 2 | 23ms |

**ローカルが速いのは当てにならない。** ローカルはUnixソケット越しなので1クエリ0.1ms程度だが、
本番は Vercel → Supabaseプーラーのネットワーク越し。1往復が数msから十数msかかるため、
**20クエリのページは往復だけで数百msになりうる**。ここが2回目以降も毎回かかっている。

### `/groups/<id>` の22クエリの内訳

| テーブル | 回数 |
|---|---:|
| `users` | **9** |
| `groups` / `group_games` | 各2 |
| その他（`albums` / `album_members` / `photos` / `group_members` / `group_game_proposals` / `group_game_interests` / `external_game_caches`） | 各1〜2 |

**半分近くが `users` への問い合わせ。** セッションからユーザーを引く1回に加えて、
オーナー・メンバー・投稿者を関連ごとに読み直している。

---

## 2. どこに時間が使われているか

1. **サーバーレスの初回起動（実測4.87秒、#33）** — キャッシュでは消せない
2. **1回の描画あたりのDB往復** — 上の表。2回目以降も毎回かかる
3. **クライアントの再訪** — 30秒以内なら0。それを過ぎると2に戻る

「一度開いたやつを速く」という観点では3が該当するが、**2を減らさないと
「30秒を過ぎた再訪」「リロード」「別端末」は速くならない。**

---

## 3. 手段

### A. セッションからユーザーIDを引けるようにする（`lib/auth.ts` のTODO）

いまは**全ページ・全APIの先頭で** `db.user.findUnique({ where: { email } })` を実行している。
該当箇所は**57箇所**（ページ10・API 33ほか）。

これは他の判定すべての前段にあり、**必ず直列で待つ**1往復。
`auth.ts:149` に `// TODO: session.user.id にDBのUser.idを詰める` として既に宿題になっている。

- 効果: 全ページ・全APIで1往復減。直列なので体感に直結する
- リスク: 低。ただし**発行済みのトークンにはidが入っていない**ため、
  移行期間はidが無ければ従来どおりDBに落とすフォールバックが要る
- 工数: 中（57箇所だが機械的）

### B. クエリそのものを減らす

`/groups/<id>` の `users` 8回のように、同じテーブルを関連ごとに読み直している。
`select` を絞る、`include` を見直す、独立したものは `Promise.all` で並べる。

- 効果: 全員・常時・キャッシュの有無に関係なく効く
- リスク: 低
- 工数: 中
- **キャッシュより先にやる価値がある。** 遅いものをキャッシュで隠すより、まず減らす

### C. DBの結果を `unstable_cache` でキャッシュする

Next.jsのデータキャッシュに載せ、更新時に `revalidateTag` で飛ばす。
外部API（Steam・ITAD）には既に同じ仕組みを使っている（`lib/steam.ts` の `gameFetchOptions`）。

- 効果: **いちばん大きい。** Vercelのデータキャッシュはインスタンス間で共有・永続なので、
  cold start直後の初回描画にも効く（AやDでは効かない領域）
- リスク: **権限。ここを間違えると他人のアルバムが見える。**
  今日直した `/albums/[albumId]` の権限漏れと同じ形の事故になりうる。
  「権限判定は毎回サーバーで行い、キャッシュするのは判定後の中身だけ」に分けるか、
  キャッシュキーにユーザーIDを含める。前者を推す
- 無効化漏れも起きやすい（投稿したのに一覧に出ない）。タグの設計を先に決めること
- 工数: 中〜大

### D. `experimental.staleTimes.dynamic` を伸ばす

`next.config.js` に数行。既定30秒を、たとえば5分にする。

```js
experimental: {
  staleTimes: { dynamic: 300, static: 300 },
}
```

- 効果: **「一度開いたやつの2回目」という今回の要望にそのまま効く。** 設定だけ
- リスク: 古い内容が出る。ただし更新操作のあとは `router.refresh()` を呼んでいる箇所が
  **36箇所**あり、自分の操作は反映される。問題になるのは**他人の投稿が最大5分見えない**こと
- 効くのは同じタブの中だけ。リロード・別端末では効かない
- 工数: 極小

### E. cold start対策（定期的に叩いて温める）

**できない。** Vercel Hobbyのcronは1日1回が上限で、枠も既に2つ埋まっている。
温め続けるには足りないので、ここは触らない。4.87秒は残る前提で考える。

## 4. 着手した順番と結果

**Dは入れないことにした。** リアルタイムに同期したいのに、他人の投稿が最大5分見えないのは
用途に合わないため。今の30秒の既定はそのまま。

AとBを入れて実測した（`tools/local-test/query-count.mjs`）。

| ページ | 変更前 | 変更後 | 増減 |
|---|---:|---:|---:|
| グループ詳細 | 22 | 6 | **-16** |
| アルバム詳細 | 12 | 5 | -7 |
| アルバム一覧 | 10 | 4 | -6 |
| ゲーム詳細 | 9 | 4 | -5 |
| ホーム | 5 | 2 | -3 |
| 未分類の投稿 | 4 | 3 | -1 |
| グループ一覧 | 2 | 1 | -1 |
| 管理・使用量 | 7 | 7 | ±0 |
| **合計** | **71** | **32** | **-39** |

内訳:

- **A（セッションにユーザーIDを載せる）で -7。** ユーザーを解決するページ・APIから1往復ずつ消えた。
  全ページの先頭にあり必ず直列で待つ1回なので、数のわりに効く
- **B（`relationJoins`）で -32。** `include` のリレーションごとに別クエリを投げる既定を、
  JOIN 1回にまとめた

`/admin` が変わらないのは、`include` を使わず個別に集計しているため（写真5回など）。
ここはクエリの書き方を変える話になるので、今回は触っていない。

**ローカルの所要時間はどれも20〜35msのままで、意味のある差は出ない。**
Unixソケット越しでは1クエリが0.1ms程度なので当然で、効くのは本番の
ネットワーク越し（1クエリ＝1往復）。**この変更の効果は本番でしか測れない。**

### 投入後に観察された挙動（2026-08-16）

「グループ→アルバムA（待つ）→グループ（一瞬）→アルバムB（待つ）→グループ（待つ）」
という報告があり、`tools/local-test/nav-probe.mjs` で同じ順番を辿って再現した。

```
[  0s] グループ（最初の表示）      ロードあり
[ 15s] → アルバムA（初回）        ロードあり
[ 16s] → グループ（戻る・直後）    ロードなし
[ 18s] → アルバムB（初回）        ロードあり
[ 19s] → グループ（戻る）         ロードなし
[ 20s] → アルバムA（2回目）       ロードなし
（35秒待つ）
[ 55s] → グループ                ロードあり
[ 57s] → アルバムA               ロードあり
```

**すべて「最後に使ってから30秒」で説明がつく。** ルーターキャッシュの再利用期限は
`lastUsedTime` からの経過で測るので、行き来している間は一瞬で、間が空くとまた取りに行く。
報告にあった「ありだったりなしだったり」は、この30秒をまたいだかどうかの差。

先読みについても測った。グループページを開くと**画面内の全リンク16件が先読みされる**が、
**DBクエリは3件しか増えない**（curlで6件 → ブラウザで9件）。動的ルートの先読みは
`loading.tsx` の骨格までで本体を描画しないため。つまり先読みはサーバー負荷の問題ではなく、
**触る必要は無い**（`prefetch={false}` を付けて回るのは逆効果）。

裏を返すと、**押した瞬間に出るのは骨格だけで、中身は必ず取りに行く**。
#33 の骨格表示と、この「ロードあり」は両立する。

## 5. C（`unstable_cache`）を入れた結果

アルバム詳細とグループ詳細の**2ページだけ**に絞って投入した。

| ページ | 変更前 | 変更後 |
|---|---:|---:|
| アルバム詳細 | 5 | **2** |
| グループ詳細 | 6 | **4** |
| 合計（8ページ） | 32 | 27 |

残っているのは**意図的にキャッシュしていない権限判定**（`hasAlbumPermission` /
`hasGroupPermission` が引くアルバム・グループ・メンバーシップ）。ここをキャッシュすると
権限の取り消しが遅れるので触らない。

### 権限まわりの決め事

- キャッシュするのは「そのアルバム／グループの中身」だけ。**「この人が見てよいか」は毎回判定する**
- **キャッシュキーにユーザーを入れない。** 入れると、キーを間違えた瞬間に他人の中身が出る
- 無効化は `lib/cacheTags.ts` の関数だけを呼ぶ（`revalidateTag` を直接書かない）。
  呼び忘れると「投稿したのに出ない」が起き、時間では直らない

### 途中で踏んだもの

**`unstable_cache` は `Date` をISO文字列にして返す。** `capturedAt?.toISOString()` が落ちたが、
**落ちるのはキャッシュヒットの回だけ**なので、1回しか開かないテストでは素通りした。
いまは日付を関数の中で文字列に直し、2回開いて確認するテスト（F62b・F64b）を足してある。

## 6. 残っている手

- **`/admin` のクエリ削減** — 7回のうち5回が photos。集計の書き方次第で減らせる
- **一覧ページのキャッシュ** — アルバム一覧・ホームは「その人に見える範囲」を返すので、
  キャッシュするならキーにユーザーが入る。**今回は入れていない**（キーの間違いが
  そのまま情報漏れになるため、やるなら単独で慎重に）
- **cold start（4.87秒）** — 打つ手が無い（Vercel Hobbyのcronは1日1回上限）

## 7. 測り直すとき

`tools/local-test/query-count.mjs` が計測する。PostgreSQLの `log_statement` を
一時的に入れて、1リクエストあたりの `LOG:  execute` を数えている。

```bash
node tools/local-test/query-count.mjs                    # 計測して表を出す
node tools/local-test/query-count.mjs --save 名前         # 結果を保存
node tools/local-test/query-count.mjs --compare 前 後      # 保存済みの2つを比較
```

**ローカルの所要時間は本番の目安にならない**（Unixソケットとネットワーク越しの差）。
見るべきはクエリ数と、それが直列かどうか。
